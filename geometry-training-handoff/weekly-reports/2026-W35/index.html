Qwen3-VL-8B 当前是怎么被调用的

是直接喂图，但不是把 PDF 原文件交给模型。当前端到端基线没有独立 OCR、视图分割或尺寸结构化模块；PDF 先渲染成图片，然后由一个通用 VLM 同时承担读图、尺寸归位、拓扑理解、CAD 规划和代码生成。

模型输入 = 1～N 张工程图 PNG + CadQuery 生成指令
模型输出 = CadQuery Python 代码（不是 STEP）
1 · PDF → PNG

每页按 200 DPI 渲染；33 件共 39 张图。多页零件保留为多张图片，不拼接。

2 · 多模态消息

同一个 user message 先放全部图像，再附文字 Prompt。推理输入不含 GT STEP。

3 · 本地 8B 推理

Transformers 在单卡加载 Qwen3-VL-8B-Instruct，BF16、greedy decoding，每件最多生成 1024 tokens。

4 · 生成 CAD 程序

Prompt 要求读取毫米尺寸、理解剖视/通孔/沉孔，并把最终 CadQuery 对象命名为 solid。

5 · 安全执行

AST 白名单拒绝文件、网络和子进程操作；合法代码在独立 CadQuery 环境中运行并导出 STEP。

6 · 自动修复一次

若安全检查或 CAD 执行失败，把错误和上一版代码连同原图再次交给模型，生成完整修正版。

7 · 独立验收

模型退出后才读取保留 GT，比较 STEP 的体积、表面积和方向无关包围盒；GT 不回流到推理。

这个设计为什么容易失败：一次生成同时承担 OCR、工程图语义、特征拓扑和 CadQuery 编程，中间没有可检查的结构化几何表示。当前结果反映的是整条端到端链路能力，不能只归因于 OCR。

数据与方法

源压缩包共识别 70 组无歧义 PDF—STEP 配对。OpenCascade 逐件读取后，保留 33 组单实体，排除 37 组多实体/装配体；30 组按同目录同名配对，3 组按唯一零件号合并多张图纸。输入共 39 张 200 DPI 图像。

每个模型在一个 GPU 作业内只加载一次；每件先生成 CadQuery，经过 AST 白名单检查后在独立 CAD Python 环境执行，首次失败允许模型修复一次。最终由独立进程读取 GT 和预测 STEP，按方向无关的排序包围盒尺寸计分。
